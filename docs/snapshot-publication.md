# نشر الحالة الحالية على MinIO

تُنشر حالة المستشعرات وملخصات Gold الحالية بإصدار Parquet مستقل غير قابل للتعديل تحت `versions/<uuid>/`. بعد نجاح كتابة كل الملفات، يُكتب `_current.json` ككائن واحد عبر S3A. نجاح إغلاق stream يحدد لحظة نشر manifest. لا يستعمل المشروع rename لمجلدات S3، لأن العملية copy/delete وليست تبديلاً ذرياً.

القارئ يقرأ manifest مرة واحدة ويحتفظ بمسار ذلك الإصدار خلال الاستعلام. فشل كتابة Parquet يترك manifest السابق دون تغيير. فشل نشر manifest يفشل batch ويمنع نشر history الخاص بها؛ قد تبقى ملفات إصدار غير مشار إليه. أخطاء الصلاحيات أو JSON أو فقد الإصدار أو تلف Parquet تنتقل إلى المشغل ولا تتحول إلى batch أولى. عند غياب manifest فقط، يسمح القارئ ببيانات Parquet القديمة الموجودة خارج `versions` والمجلدات المؤقتة.

Gold يستخدم event time واختيار `reading_id` ثابت عند التعادل في حالة المستشعر. ملخصات المنطقة والمزرعة تُحسب من جميع المستشعرات الحالية وتُنشر كاملة: استخدام max event time وحده لتبديل الملخص قد يفقد قراءة متأخرة من مستشعر آخر. تُنشر مؤشرات ملخصَي المنطقة والمزرعة قبل كتابة مسارات history التي تراقبها عملية ClickHouse. history تبقى تحت مسارات batches منفصلة، ولا تحتوي إصدارات mutable latest.

يجب وجود كاتب واحد لكل snapshot/checkpoint. `_current.json` ليس قفل كتابة موزعاً ولا يوفر معاملة تشمل جميع datasets. الضمان الذري للكائن خاص بـMinIO/S3A؛ الكتابة المحلية لنفس الملف أثناء قراءته لها قواعد مختلفة. فشل الشبكة أثناء close قد يجعل نتيجة PUT غير مؤكدة؛ إعادة batch والتحقق من manifest يستعيدان الحالة دون حذف البيانات القديمة.

الإصدارات السابقة والأيتام محفوظة عمداً ولا توجد عملية حذف تلقائية. تحتاج garbage collection لاحقاً إلى سياسة احتفاظ ومساحة كافية، وإلى ضمان عدم وجود قارئ يستخدم إصداراً سيُحذف. حذف آخر إصدار أو استعمال سياسة lifecycle قصيرة قد يكسر الاستعلامات. الاختبارات تحاكي commit-on-close للكائن وتتحقق من حالات الفشل والاسترداد وترتيب نشر snapshots قبل history؛ يبقى اختبار Spark وS3A الحي مطلوباً عند توفر Docker.
