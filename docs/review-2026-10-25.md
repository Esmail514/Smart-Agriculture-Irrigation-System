# مراجعة المشروع — 25 أكتوبر 2026

هذه مراجعة إضافية للكود الحالي، تشمل التطبيق والموقع المشتركين في Flutter، وAPI والتحكم، وPipeline وML والطقس والتشغيل. أُنجزت بالتوازي مع ثلاثة subagents؛ النتائج أدناه تميز اختبارات الكود عن التشغيل الحي.

## الإصلاحات

- **التطبيق والموقع:** خروج محلي فوري وحماية الجلسة الجديدة من طلب خروج قديم؛ انتظار عمليات تخزين رموز الجلسة المعلقة قبل قراءتها؛ منع بقاء سجلات مورد سابق قابلة للتحرير عند فشل تحميل مورد آخر؛ تحديث قائمة المزارع بعد تعديل catalog والتعامل مع حذف المزرعة المختارة؛ إزالة حرارة تربة ثابتة من تفاصيل الحقل؛ تصحيح إعادة محاولة تحميل telemetry وحالة عدم توفر التوقعات.
- **API:** إبطال توصيات الحقول والتنبيهات عند تغيير حدود المحصول أو جرعة الماء حتى لو بقي crop_id نفسه. تأكيد التنبيه يعيد فحص القاعدة داخل transaction. تبقى القياسات المرصودة ظاهرة عند إبطال التوصية. الطوابع الزمنية التالفة وقيم JSON غير الصالحة لا تتحول إلى أخطاء داخلية أو بيانات صحيحة ظاهريًا. إتاحة مسح city/district الاختياريين وفك ربط actuator بمنطقة عبر null مع استمرار رفض null للحقول المطلوبة.
- **Pipeline:** يستخدم تصنيف Bronze وقت Kafka الثابت بدل ساعة تنفيذ كل query، لمنع اختلاف التصنيف بين accepted وquarantine عند إعادة المعالجة. تبقى البيانات المرفوضة خارج Bronze. metadata الخاصة بالحساسات والقواعد snapshot ثابت ومحدود الذاكرة عند بدء المستهلك، فلا تتغير نتيجة خطتين مستقلتين بسبب إعادة قراءة JDBC.
- **ML والطقس:** ربط زمني لا يضم aggregate طقس أحدث من القياس، وفحص صلاحية خصائص الطقس. لا تزال aggregates اليومية خارج تدريب النموذج لعدم وجود أرشيف نشر تاريخي موثوق. الحفاظ على IDs الصحيحة ذات 64 بت بدل فقد دقتها خلال iterrows.
- **التشغيل:** LocalExecutor متوافق مع الخدمات الموجودة؛ تثبيت dependencies أثناء بناء صور Airflow/Spark؛ init قابل للإعادة ويفشل بوضوح؛ إلغاء قتل streams الدوري؛ تشغيل batch المحدود دون انتظار خلف streams الدائمة؛ منع إطلاق stream مكرر وفحص exit codes؛ runner يحترم profiles ويفحص نجاح init؛ إيقاف الخدمات يحفظ volumes.

## Schema والمراقبة

يبقى الاختيار Star Schema لحقائق وأبعاد ClickHouse، مع نموذج تشغيلي مطبّع في PostgreSQL وعقود صريحة للطبقات. التفاصيل في [data-model-v2.md](data-model-v2.md). تعرض dashboards حالات البيانات المفقودة دون اختلاق قياسات، ويفصل رصد Prometheus صحة الخدمات وHTTP عن تحليلات الزراعة؛ راجع [observability-deployment.md](observability-deployment.md).

## التحقق

- Python: **283 اختبارًا ناجحًا** عبر `pytest tests -q -m 'not integration'`.
- فحص Flake8 للأخطاء القاطعة ناجح، وCompose لجميع profiles صالح، وفحوص Bash وPowerShell ناجحة.
- أُعيد توليد [OpenAPI](api-openapi.json): 43 مسارًا.
- Spark 3.5.0 / Java 17 داخل حاوية معزولة بلا شبكة: نجحت مجموعات التحقق الثلاث في `tests/integration/spark_contract_smoke.py`؛ تشمل snapshot ذات schema وLong64 وDecimal وUTC وحد الجمع، وتقسيم عشر حالات مستشعر إلى accepted/quarantine دون ازدواج، والتحقق من Weather Silver وإزالة التكرار.
- بُنيت صورة Airflow، وحُمّلت المهام الثلاث دون import errors. نجح promtool في التحقق من config وقواعد التنبيه التسع واختباراتها، وفي تحليل تعبيرات PromQL الـ23 في Grafana.
- Flutter: **60 اختبارًا ناجحًا** و`flutter analyze` دون مشاكل. استُعيدت مكتبة `fl_chart 0.70.2` بالبصمة المطابقة لـ`pubspec.lock` دون ترقية الاعتمادات. صُحح finder لاختبار dialog لتمييزه عن dropdown الموجود في الخلفية؛ لم يتطلب ذلك تغيير سلوك المنتج.
- نجح `flutter build web --dart-define=API_BASE_URL=http://localhost:8000` وأُنتج `App/build/web`. هذا عنوان مراجعة محلي؛ يحتاج النشر إلى عنوان API فعلي وHTTPS. البناء JavaScript ناجح، بينما dry-run لـWasm يبلغ عدم توافق اعتماد التخزين الآمن؛ لا يُعد ذلك دعمًا لـWasm. لم تُجر معاينة بصرية جديدة في هذه المتابعة.

## متطلبات الترقية وحدود التحقق

أصبح محرك Docker Linux 29.7.2 متاحًا أثناء المراجعة. نجح اختبار معزول على PostgreSQL 16 في ذاكرة مؤقتة: تحميل schema، تسجيل الدخول، قراءة كتالوج الإدارة، مسح الحقول الاختيارية، إنشاء actuator، فحص صلاحيات المزرعة، تدوير refresh token ورفض access token القديم. نجح تحميل ملفي schema على ClickHouse 26.5.1.882، وإنشاء الأبعاد والحقائق، وقراءة سجل واحد بالنسخة الأحدث بعد إدراج سجلين متكررين، وتنفيذ EXCHANGE TABLES للأبعاد. أُوقفت حاويتا الاختبار وحُذفتا بعد الفحص، دون استخدام volumes المشروع.

لم تُشغّل migrations على قواعد المستخدم ولم يُختبر مسار Kafka→MinIO→ClickHouse كاملًا أو DAGs عبر stack حي. تعليمات البناء والتحقق والترقية في [deployment-review.md](deployment-review.md).

في متابعة المراجعة تعطل بدء Docker Desktop قبل توفير Engine بسبب `sailor-ingest.sock`؛ لم تستعده محاولة إعادة التشغيل المدعومة. لذلك بقي بناء صور Spark وAPI وcontrol-agent دون تحقق مكتمل. تفاصيل العطل والمحاولة في دليل التشغيل، ولم يُجر reset أو حذف لبيانات Docker.

يجب ضبط **topic Kafka الموجود** على `LogAppendTime` صراحة وفق الدليل؛ إنشاء topic مع if-not-exists لا يغير الإعداد القديم. المستهلكون يحملون metadata عند البدء؛ أعد تشغيل streams بعد تغيير catalog/rules. الحد الافتراضي `METADATA_SNAPSHOT_MAX_ROWS=100000`، وتجاوزه يوقف البدء بوضوح.

أوامر الري تبقى queued حتى توصيل executor حقيقي موثق؛ قبول الأمر لا يثبت تشغيل مضخة. النموذج يصف الجفاف الحالي، ولا يدّعي توقع احتياج الغد. لا تعني الاختبارات المحلية ضمان خلو المشروع من كل عيب أو بديلًا لاختبار تكامل حي.

لم تُبن حزم Android/iOS ولم يُختبر التطبيق على هاتف حقيقي في هذه المراجعة. نشر Android يحتاج إعداد هوية التطبيق ومفتاح توقيع إصدار خاص بالمشروع؛ إعداد Gradle الحالي ما زال يستخدم توقيع debug للإصدار المحلي.
